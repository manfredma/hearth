# Hearth 产品 Backlog

> 更新日期：2026-09-24
>
> 本文记录 Hearth MVP 之后的产品和工程待办。Backlog 不等同于当前版本承诺；每项工作开始前仍需补充设计、接口契约、测试和发布计划。

## MVP 发布基线

当前 MVP 已覆盖统一认证的核心闭环，可以先发布并接入业务系统：

- Hearth 本地账号登录、CSRF 防护和服务端 Session。
- 30 天免登录 Remember-Me 凭据。
- OIDC Discovery、Authorization Code + PKCE、Token、JWKS 和 UserInfo。
- OAuth 授权确认页，以及 `profile`、`email` scope 的选择。
- Career 等业务系统的 RP-Initiated Logout 与 Hearth 统一退出。
- Hearth 首页身份概览、已接入应用展示、移动端菜单和账户退出入口。
- MySQL 身份数据、Redis Session，以及 staging/生产环境隔离。

以下事项不阻塞 MVP 的核心认证发布，但不能在产品说明中宣称已经完成。

## P0：接入前必须补齐

### 用户注册与人员初始化

- **状态**：未开始
- **目标**：提供受控的人员注册 API，供 Agent 或运维初始化账号；默认不开放匿名公开注册页面。
- **范围**：用户名唯一性、显示名、密码策略、启用/禁用、重复注册幂等语义、错误码、审计事件、staging/生产环境隔离。
- **验收**：Agent 可以通过明确认证的 API 创建人员；创建后可以直接登录并完成 OIDC 授权；密码只保存哈希，不出现在日志和响应中。

### 账户资料基础能力

- **状态**：未开始
- **目标**：提供当前用户资料读取和有限更新能力。
- **范围**：显示名、头像、邮箱展示与修改；用户名和稳定 subject 不允许普通用户修改。
- **验收**：Hearth、OIDC UserInfo 和已接入系统看到的资料来源一致；修改后无需重新创建业务系统本地用户映射。

## P1：管理控制台完整化

### 应用接入管理页面

- **状态**：后端部分存在，界面未实现
- **目标**：把当前静态的“应用接入”入口改成真实管理页面。
- **范围**：应用列表、详情、创建、编辑、禁用/撤销；OAuth Client ID、登录回调地址、退出回跳地址、scope 配置；Secret 只在创建时返回一次。
- **验收**：页面数据来自后端，不再写死应用名称、数量或状态；登录回调地址和退出回跳地址始终分开管理。

### 应用授权与同意管理

- **状态**：授权流程已实现，管理界面未实现
- **目标**：用户可以查看已经授权的应用并撤销授权。
- **范围**：按用户展示应用、scope、授权时间；撤销后清理 consent，后续访问必须重新同意；明确撤销是否同时吊销 Token。
- **验收**：撤销操作有确认、成功反馈和审计记录；业务系统不能继续使用已撤销的长期授权结果。

### 安全设置页面

- **状态**：导航入口存在，页面未实现
- **目标**：将“安全设置”从静态导航变成真实功能页。
- **范围**：修改密码、密码强度提示、当前会话退出、全部会话退出、Remember-Me 凭据失效；密码找回流程另行设计。
- **验收**：敏感操作要求当前密码或重新认证；完成密码变更后旧的长期登录凭据按策略失效。

### 会话与设备管理

- **状态**：未开始
- **目标**：让用户看到并管理自己的登录设备和长期会话。
- **范围**：设备标识、最近活动时间、登录来源、单设备撤销、全部撤销；不展示原始 Cookie、Token 或密码。
- **验收**：撤销动作能够使对应服务端 Session 和 Remember-Me 凭据失效，并有可追踪审计事件。

### 真实的总览与应用详情

- **状态**：当前为静态原型
- **目标**：让总览页反映真实身份和应用状态。
- **范围**：接入应用数量、最近授权、当前会话状态、应用卡片详情和安全摘要全部从 API 获取；“帮助文档”“管理接入”按钮必须有真实行为。
- **验收**：应用新增、撤销或状态变化后，页面无需重新发布前端代码即可正确展示。

## P2：体验与运营能力

### 弹窗登录

- **状态**：未开始，已确认作为后续体验优化
- **目标**：桌面端登录使用类似 Google 的 OAuth 弹窗，减少业务页面整体跳转。
- **范围**：Career 打开 Hearth 授权弹窗；回调页通过严格校验的 `postMessage` 通知父窗口；父窗口刷新本地 Session；移动端、弹窗被拦截或通信失败时回退整页登录。
- **安全约束**：不把 access token、ID token 或密码交给前端父窗口；严格校验来源 origin、state 和 nonce；弹窗关闭、超时、拒绝授权都要有可理解的错误状态。

### 帮助文档与故障引导

- **状态**：按钮未实现
- **目标**：提供登录、授权、退出、30 天免登录和常见错误的用户说明。
- **验收**：帮助入口在桌面和移动端都可用；403、授权拒绝、会话过期等场景有明确下一步操作。

### 安全审计与运营查询

- **状态**：领域表结构已有基础设计，查询界面未实现
- **目标**：为账号、授权、注册、登录失败、登出、撤销和管理员操作提供审计能力。
- **验收**：审计记录不包含密码、Cookie、Token 原文；管理员可以按用户、应用、时间和事件类型查询。

### 多因素认证与恢复流程

- **状态**：未开始
- **目标**：在基础认证稳定后增加 MFA、恢复码和受控密码找回。
- **验收**：先补充独立安全设计和威胁模型，再进入实现；恢复流程不能绕过应用身份映射和会话撤销策略。

## 明确不放入 Hearth 的范围

- 各业务系统的菜单、功能权限、角色和数据权限。
- Career、Daylilt、Toolbox 等系统内部对象的访问控制。
- 各业务系统的业务数据、业务审计和业务工作流。

Hearth 负责“你是谁、是否完成认证、是否允许业务应用建立 OIDC 会话以及统一退出”；业务系统继续负责“你在本系统能做什么”。

## Backlog 执行规则

1. P0 项目优先补充 API 契约、数据模型、权限边界和单元测试。
2. 涉及账号、Token、Session、授权或密码的事项，必须先补 ADR 或更新既有 ADR。
3. 所有用户可见页面改动必须在 staging 完成集成测试和 E2E 验收。
4. 每项完成后从本文移除对应“未开始/部分实现”描述，保留必要的验收记录链接。
