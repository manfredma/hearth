# ADR-0010: 业务应用不提供自有登录入口

- **状态**: Accepted
- **日期**: 2026-09-23
- **决策者**: 项目所有者

## 上下文

接入 Hearth 的业务系统不应重复建设账号密码登录页面。业务系统仍需要处理未认证访问、登录按钮和 OIDC 回调，但“是否必须提供 `/login`”容易把用户体验入口与协议路由混为一谈。

深链接场景要求用户登录后回到原始业务地址；这可以由 OAuth `state` 和客户端的 saved request 机制完成，不依赖业务系统提供 `/login`。

## 决策

业务系统不提供自有的 `/login` 页面或必需的 `/login` 接口，也不收集或校验 Hearth 用户密码。

- 用户点击登录按钮时，直接发起业务系统配置的 OIDC Authorization Code + PKCE 流程。
- 用户访问受保护的浏览器页面且没有本地 Session 时，业务系统直接重定向到 Hearth 授权端点。
- OIDC 回调接口由客户端框架提供，例如 `/login/oauth2/code/hearth`；该路径是协议回调，不是业务登录页面。
- 登录完成后由 `state`/saved request 恢复原始深链接。
- 未认证 API 返回 `401 Unauthorized`，不返回业务登录 HTML。
- 真正的账号密码登录页面只存在于 Hearth。

放弃为每个业务系统增加薄 `/login` 跳转接口作为默认约定；它只能提供书签或显式入口便利，不能增加认证能力，且容易让团队误以为业务系统拥有独立登录职责。

## 后果

**正向**

- 业务应用的认证入口和密码处理边界更清晰。
- 不需要为每个系统维护重复的登录页面、错误文案和登录状态。
- 深链接、登录按钮和未认证访问都可以直接复用标准 OIDC 流程。

**负向**

- 各客户端必须正确配置 OIDC 授权启动和回调路径。
- 用户在业务系统看到的登录按钮需要由各应用自己渲染。
- 不同客户端框架可能使用不同的内部回调路径，但不能改变 Hearth 的协议端点。

## 假设

| 假设 | 可证伪信号（出现时重评） |
|------|--------------------------|
| 所有接入应用可以使用标准 OIDC 客户端 | 遗留应用无法在不增加适配层的情况下发起 Authorization Code 流程 |
| 客户端框架可以保存原始请求并在回调后恢复 | 关键应用无法可靠实现 state/saved request 安全校验 |

## 退出条件

| 信号 | 预设行动 |
|------|----------|
| 某类客户端必须拥有独立的交互式认证入口 | 单独评估该客户端适配层，不恢复业务系统自有密码登录 |
