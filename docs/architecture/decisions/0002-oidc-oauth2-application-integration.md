# ADR-0002: 使用 OIDC 与 OAuth 2.0 接入业务应用

- **状态**: Proposed
- **日期**: 2026-09-22
- **决策者**: 项目所有者

## 上下文

多个 Web 应用需要统一登录，同时需要让应用或 API 能够验证登录结果和受限访问令牌。自定义登录跳转、Token 格式和跨应用 Cookie 会造成协议和安全维护负担。

## 决策

Hearth 与业务应用之间采用 OpenID Connect；需要 API 访问授权时采用 OAuth 2.0。Web 应用使用 Authorization Code + PKCE。ID Token 用于确认用户身份，Access Token 用于受限 API 访问；业务权限仍由业务系统执行。

放弃跨应用共享 Session Cookie，因为它扩大 Cookie 信任域并让应用之间产生不必要的耦合。放弃自定义 Token，因为无法复用成熟的客户端和资源服务器实现。

## 后果

**正向**

- Spring Boot、React 和其他技术栈可以使用成熟的 OIDC 客户端。
- 每个应用拥有独立 Client、回调地址和本地会话边界。
- 可以按应用和 API 使用最小化 Scope。

**负向**

- 需要管理 Client、回调地址、密钥、Issuer 和 Token 生命周期。
- 登出和权限变更需要设计本地会话失效策略。
- Access Token 中的角色声明可能短暂过期，敏感操作仍需服务端实时校验。

## 假设

| 假设 | 可证伪信号（出现时重评） |
|------|--------------------------|
| 各业务应用可以使用标准 OIDC 客户端 | 某个必须接入的遗留应用不支持 OIDC 且无法增加适配层 |
| Web 应用可使用服务端会话或 BFF | 主要客户端转为纯原生移动端或设备端 |

## 退出条件

| 信号 | 预设行动 |
|------|----------|
| 某类客户端无法安全使用 Authorization Code + PKCE | 为该客户端单独评估 Device Authorization 或其他标准流程，不修改 Web 应用默认流程 |
