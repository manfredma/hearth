# ADR-0008: 业务应用按稳定 subject 建立本地用户映射

- **状态**: Accepted
- **日期**: 2026-09-23
- **决策者**: 项目所有者

## 上下文

Hearth 集中维护统一身份，但 Career、bytedepth、daylilt 等应用仍需要自己的用户记录、`owner_id`、业务角色和数据归属。应用不能直接读取 Hearth 数据库，也不能用可能变化或重复的用户名、邮箱作为跨系统主键。

注册完成后，应用还需要明确知道何时创建本地用户，以及一个 Hearth 身份如何关联到已有业务数据。

## 决策

Hearth 是身份注册和身份生命周期的唯一来源；业务应用通过 OIDC 登录结果中的 `iss + sub` 建立本地用户映射，不共享 Hearth 数据库。

默认采用“允许访问后的首次登录自动创建本地用户”（JIT provisioning）：

1. 用户在 Hearth 注册或被启用。
2. Hearth 根据应用访问关系决定是否允许该用户启动某个 Client。
3. 应用完成 Authorization Code + PKCE 回调，验证 `iss`、签名、`aud`、`exp` 和 nonce。
4. 应用使用 `issuer + subject` 查找本地映射。
5. 映射不存在时，应用根据自己的策略创建本地用户、`owner_id` 和默认业务角色；存在时复用已有业务数据。

需要审批或邀请的应用可以关闭自动创建，改为由应用管理员预先创建映射。已有本地数据的迁移必须通过显式映射完成，禁止仅凭同名用户名自动合并。

业务应用可以使用 Hearth 的应用访问 API 或管理界面维护“是否允许进入应用”，但用户进入应用后的角色、功能权限、资源权限和数据权限由业务应用自己决定。

## 后果

**正向**

- Hearth 不需要理解 Career、博客或日记的业务数据模型。
- 应用可以保留自己的 `owner_id` 和权限模型，同时获得统一登录。
- 用户修改用户名或邮箱不会破坏已有业务数据关联。
- 首次登录可以减少跨系统人工建号工作。

**负向**

- 每个应用都需要实现本地映射和首次登录策略。
- 账号禁用、删除和本地用户清理需要定义跨系统生命周期处理。
- JIT 创建必须结合应用访问控制，否则可能让任意 Hearth 用户进入不应访问的应用。

## 假设

| 假设 | 可证伪信号（出现时重评） |
|------|--------------------------|
| OIDC `sub` 在同一 `issuer` 内稳定且唯一 | Hearth 需要重建用户身份或改变 subject 语义 |
| 大多数内部应用可以接受首次登录时创建本地映射 | 审批、合规或计费要求所有本地账号必须预先批准 |
| 应用访问关系与业务角色可以分离 | 多个应用要求 Hearth 事务性地执行相同业务授权规则 |

## 退出条件

| 信号 | 预设行动 |
|------|----------|
| JIT provisioning 导致未授权用户进入应用 | 默认改为邀请/预创建映射，并强制应用访问审批 |
| 多个系统需要统一、实时且可审计的业务授权 | 单独评估权限服务，不把业务权限直接塞入 Hearth 身份目录 |
