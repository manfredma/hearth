# ADR-0013: Agent 技术验收与项目所有者最终验收的职责边界

- **状态**: Accepted
- **日期**: 2026-09-24
- **决策者**: Hearth 项目所有者

## 上下文

Hearth 的认证链路包含浏览器、Career、Hearth、Redis、MySQL、OAuth 2.0 授权码流程和 OIDC 回调。单元测试或“页面能打开”不能证明整条链路可用。最近一次 staging 验收中，OAuth 授权码换 Token 时缺少 `auth_time`，导致 Career 回调失败并反复重定向；这是每次都可以复现的工程缺陷，不应由项目所有者在最终验收阶段代为发现。

项目所有者仍然需要确认产品是否符合预期，包括交互语义、视觉质量、业务流程和是否可以放行。但最终验收不是工程测试的替代品。

## 决策

Agent 在交付 staging 验收前，必须先独立完成并保留可复核的技术验证；项目所有者只承担产品与最终放行验收。职责边界如下：

| 事项 | Agent 负责 | 项目所有者负责 |
|------|------------|----------------|
| 编译、单元测试、静态分析、覆盖率 | 必须完成并修复失败 | 不承担发现职责 |
| 服务启动、数据库迁移、配置和依赖健康 | 必须完成并检查日志 | 不承担发现职责 |
| 关键跨服务流程和 E2E | 必须使用 staging、测试账户或可控 fixture 验证 | 可抽查，不替代 Agent 验证 |
| 必现的错误、异常日志、重复重定向、HTTP 状态错误 | 必须在交付前定位并修复 | 不应作为首次发现者 |
| 产品语义、视觉、文案、交互偏好 | 提供可验收版本并自检明显问题 | 负责最终判断是否符合预期 |
| 最终放行 | 提供 commit-bound 测试和部署证据 | 明确验收通过或拒绝放行 |

交付 staging 前至少要有以下证据：

1. 当前候选提交通过本地质量门禁；
2. staging 服务健康，迁移完成，日志中没有本次变更相关的 `ERROR`、异常栈或告警；
3. 关键用户路径已由 Agent 在 staging 实际执行，包括登录、授权同意、回调、Token 交换和目标页面访问；
4. 对重定向类问题记录最终 URL、HTTP 状态、重定向次数和服务端对应日志；
5. 测试和部署证据绑定当前候选提交的完整 SHA。

如果 Agent 无法独立完成 E2E（例如缺少测试账号、环境不可用或外部依赖故障），必须明确报告阻塞原因，不得把未验证的必经路径直接交给项目所有者反复尝试。

## 后果

**正向**

- 项目所有者的验收时间用于确认产品价值和体验，而不是重复发现基础工程缺陷。
- 必现问题会在进入验收前被自动化或人工 E2E 捕获，减少“改一次、让用户试一次”的往返。
- 每次 staging 验收都有可复核的提交、环境、日志和流程证据。

**负向**

- Agent 交付前需要维护测试账户、fixture、E2E 流程和证据记录，验证成本会上升。
- 视觉和产品判断仍不能完全自动化，项目所有者仍需要进行最终验收。
- staging 不可用时不能用本机结果冒充跨服务验收，可能导致交付暂停。

## 假设

| 假设 | 可证伪信号（出现时重评） |
|------|--------------------------|
| staging 是跨服务登录链路的唯一可信验收环境 | staging 与生产拓扑或配置差异导致验证结果不具代表性 |
| 关键认证链路可以使用专用测试账户或 fixture 重复执行 | 无法在不接触项目所有者私人凭据的情况下完成完整流程 |
| 测试、日志和部署记录可以绑定候选提交 SHA | 记录缺少完整 SHA，或部署后运行代码与记录不一致 |

## 退出条件

| 信号 | 预设行动 |
|------|----------|
| 连续发生必现问题在项目所有者验收阶段才被发现 | 增加对应 E2E、健康检查或日志断言，并暂停交付直到证据补齐 |
| Agent 只能通过项目所有者手工操作才能验证关键路径 | 建立受控测试账户/fixture；无法建立时将任务标记为阻塞，不宣称可验收 |
| staging 结果与生产行为长期不一致 | 重新评估环境隔离和发布拓扑，补充生产等价性检查 |
